# Sistemas Distribuidos: Fundamentos

## Definición

Un sistema distribuido está compuesto por múltiples procesos o nodos independientes que cooperan mediante una red para ofrecer una capacidad común. A diferencia de una aplicación monolítica ejecutada en un único proceso, los componentes pueden fallar de manera independiente. Cada nodo puede tener una visión parcialmente diferente del estado global del sistema. La comunicación entre componentes ocurre mediante redes que introducen latencia y posibles pérdidas. Un nodo puede dejar de responder mientras los demás continúan funcionando normalmente. Los procesos también pueden reiniciarse sin que el resto del sistema se detenga. La coordinación entre componentes requiere mecanismos explícitos de comunicación y sincronización. La ausencia de memoria compartida obliga a los procesos a intercambiar información mediante mensajes. El sistema debe considerar que una respuesta puede tardar más de lo esperado o no llegar nunca. Las decisiones de diseño deben contemplar fallos parciales, concurrencia y comunicación remota. El objetivo principal es proporcionar una capacidad coherente aunque los componentes individuales puedan experimentar problemas. Esta característica diferencia fundamentalmente a los sistemas distribuidos de los programas que se ejecutan completamente dentro de un único proceso.

## Propiedades importantes

### Latencia de red

Una llamada entre servicios no equivale a una llamada a una función local. Una función dentro del mismo proceso puede ejecutarse en microsegundos. Una llamada HTTP puede tardar varios milisegundos incluso cuando todos los componentes están disponibles. La latencia puede aumentar cuando existen múltiples saltos entre servicios. Los routers, balanceadores y proxies también pueden introducir retrasos adicionales. Una red congestionada puede provocar tiempos de respuesta mucho mayores que los habituales. La distancia física entre los centros de datos también puede afectar la latencia. Una aplicación distribuida debe establecer límites razonables para esperar respuestas. Los clientes no deberían permanecer bloqueados indefinidamente esperando una dependencia. Por eso una comunicación entre servicios debe asumir que la red puede fallar. Los timeouts permiten convertir una espera indefinida en un fallo controlado. Sin límites de tiempo, una dependencia lenta puede terminar consumiendo todos los recursos disponibles del servicio consumidor. Este problema puede propagarse progresivamente hasta afectar a una parte mucho mayor del sistema.

### Fallos parciales

En un sistema distribuido, un componente puede estar funcionando mientras otro está caído. Un servicio puede responder correctamente a algunas solicitudes y fallar en otras. Una base de datos puede estar disponible mientras una cola de mensajes deja de responder. Un nodo puede perder conectividad con el resto del sistema sin estar realmente detenido. Desde la perspectiva de otros componentes, un proceso inaccesible puede parecer simplemente caído. El sistema completo debe decidir qué hacer cuando una dependencia no responde. Algunas operaciones pueden degradarse temporalmente en lugar de fallar completamente. Otras operaciones pueden requerir que el sistema rechace la solicitud para preservar la integridad de los datos. Los fallos parciales son especialmente difíciles porque no existe necesariamente una señal global que indique qué está ocurriendo. Cada componente puede observar una situación diferente al mismo tiempo. Por esta razón los mecanismos de recuperación deben diseñarse explícitamente. La detección de fallos suele depender de timeouts, health checks y otras señales de infraestructura. Una arquitectura robusta limita la propagación de un fallo local hacia otros componentes.

### Consistencia

La consistencia describe qué tan sincronizadas están las observaciones de los datos entre diferentes nodos. Dos clientes pueden consultar réplicas diferentes y recibir valores distintos durante un periodo determinado. La consistencia fuerte intenta garantizar que las lecturas observen un estado actualizado de acuerdo con reglas estrictas. Esto normalmente requiere coordinación adicional entre los nodos participantes. La coordinación puede incrementar la latencia de las operaciones. También puede reducir la disponibilidad cuando algunos nodos dejan de comunicarse. La consistencia eventual permite que diferentes réplicas converjan después de que ocurre una actualización. Durante el periodo de convergencia algunos clientes pueden observar valores anteriores. Este comportamiento puede ser aceptable para determinados casos de uso. Un contador financiero puede requerir garantías mucho más estrictas que una métrica de visitas. La elección del modelo de consistencia debe depender de las necesidades reales del negocio. No existe un único nivel de consistencia que sea ideal para todas las operaciones. Elegir consistencia fuerte para todo puede generar costos innecesarios. Elegir consistencia eventual para todo puede provocar comportamientos incorrectos en operaciones críticas.

### Disponibilidad

La disponibilidad representa la capacidad del sistema de responder a solicitudes. Un sistema altamente disponible intenta continuar operando incluso cuando algunos componentes presentan fallos. La replicación puede permitir que una instancia continúe atendiendo solicitudes mientras otra está fuera de servicio. Los balanceadores pueden distribuir tráfico entre múltiples instancias saludables. Los mecanismos de failover también pueden cambiar automáticamente hacia componentes alternativos. Sin embargo, aumentar la disponibilidad suele introducir complejidad adicional. Las réplicas deben mantenerse coordinadas y los cambios de estado deben propagarse correctamente. Una arquitectura puede sacrificar parte de la consistencia inmediata para mantener operaciones disponibles durante ciertos fallos. Esta decisión puede ser razonable cuando los datos toleran pequeñas ventanas de inconsistencia. En otros casos la disponibilidad no puede priorizarse sobre la integridad de la información. Una transferencia bancaria, por ejemplo, puede requerir garantías diferentes a una aplicación de contenido. La disponibilidad también debe medirse con métricas concretas y no solamente con afirmaciones generales. Un sistema que responde lentamente puede considerarse técnicamente disponible pero resultar inútil para los usuarios. Por eso la disponibilidad debe analizarse junto con latencia, errores y capacidad de recuperación.

## Comunicación síncrona y asíncrona

La comunicación síncrona normalmente utiliza HTTP o gRPC y hace que el consumidor espere una respuesta. El consumidor realiza una solicitud y permanece involucrado en la operación hasta recibir una respuesta. Este modelo es sencillo de comprender porque el flujo de ejecución mantiene una relación directa entre solicitud y resultado. Es adecuada cuando el consumidor necesita conocer inmediatamente el resultado. Sin embargo, una dependencia lenta puede bloquear recursos del servicio que realizó la llamada. Las cadenas de llamadas síncronas también pueden aumentar la latencia total de una operación. Si un servicio A llama a B y B llama a C, el resultado de A puede depender de todos ellos. La comunicación asíncrona utiliza mecanismos como colas o streams de eventos. El productor publica un mensaje y el consumidor lo procesa posteriormente. Esto desacopla temporalmente los componentes y permite que cada uno procese trabajo a su propio ritmo. Una cola puede absorber temporalmente una carga elevada mientras los consumidores procesan los mensajes disponibles. El procesamiento asíncrono también permite ejecutar tareas que no necesitan bloquear la solicitud original. Sin embargo, introduce nuevos problemas relacionados con duplicados, orden de mensajes y consistencia eventual. Por lo tanto, pasar de comunicación síncrona a asíncrona no elimina la complejidad, sino que cambia el tipo de complejidad que debe manejar el sistema.

## Idempotencia

Una operación idempotente puede ejecutarse varias veces sin producir un efecto final diferente al de ejecutarla una sola vez. La idempotencia es especialmente importante cuando existen reintentos. Una solicitud puede llegar correctamente al servidor pero perderse la respuesta antes de llegar al cliente. El cliente podría interpretar esta situación como un fallo y enviar nuevamente la misma operación. Si la operación no es idempotente, el segundo intento puede producir un efecto adicional. Un endpoint que procesa un pago no debería cobrar dos veces solamente porque el cliente reintentó una solicitud después de un timeout. Una clave de idempotencia puede asociar una solicitud lógica con un resultado ya procesado. El servidor puede almacenar esa clave y reconocer solicitudes repetidas. Cuando recibe una solicitud duplicada, puede devolver el resultado previamente generado. Esta estrategia requiere definir cuánto tiempo deben conservarse las claves de idempotencia. También es necesario decidir qué ocurre cuando una misma clave aparece asociada con parámetros diferentes. La idempotencia debe considerarse tanto en las APIs como en los consumidores de mensajes. Un worker que procesa un evento puede recibir el mismo mensaje más de una vez. Diseñar los efectos secundarios para tolerar duplicados reduce considerablemente el riesgo de inconsistencias.

## Timeouts y reintentos

Todo cliente que dependa de una red debería tener límites de tiempo razonables. Un timeout evita esperar indefinidamente por una respuesta que posiblemente nunca llegará. El valor del timeout debe considerar el comportamiento esperado de la dependencia. Un timeout demasiado pequeño puede generar fallos innecesarios durante picos normales de latencia. Un timeout demasiado grande puede mantener recursos ocupados durante demasiado tiempo. Los reintentos no deben aplicarse indiscriminadamente. Reintentar una operación de lectura puede ser relativamente seguro si es idempotente. Reintentar una operación que modifica datos puede duplicar efectos si no existe protección. También es importante limitar el número máximo de reintentos. Una estrategia común consiste en utilizar exponential backoff. El intervalo entre intentos aumenta progresivamente después de cada fallo. Puede añadirse jitter para evitar que muchos clientes reintenten exactamente al mismo tiempo. Sin jitter, miles de clientes pueden generar una nueva carga simultánea después de una interrupción. Los reintentos excesivos pueden transformar una dependencia degradada en una dependencia completamente saturada. Por esta razón los timeouts y reintentos deben diseñarse como parte de una estrategia global de resiliencia.

## Circuit breaker

Un circuit breaker evita continuar enviando solicitudes a una dependencia que está fallando repetidamente. Su objetivo es limitar la cantidad de trabajo enviado hacia un componente que probablemente no pueda procesarlo correctamente. El patrón puede pasar por estados como Closed, Open y Half-Open. En estado Closed las solicitudes fluyen normalmente hacia la dependencia. El circuit breaker registra los fallos y puede calcular tasas de error o ventanas de tiempo. Cuando se alcanza determinado umbral, el circuito cambia al estado Open. En Open las llamadas se rechazan rápidamente sin intentar contactar con la dependencia. Esto permite liberar recursos del servicio consumidor y evitar esperas innecesarias. Después de un periodo determinado, el circuito puede pasar a Half-Open. En Half-Open se permiten algunas solicitudes de prueba para determinar si la dependencia se recuperó. Si las pruebas tienen éxito, el circuito puede volver a Closed. Si vuelven a producirse fallos, el circuito puede regresar a Open. La configuración de los umbrales debe basarse en el comportamiento real del sistema. Un circuit breaker mal configurado puede abrirse demasiado fácilmente o reaccionar demasiado tarde. Por eso debe observarse junto con métricas de errores, latencia y disponibilidad.

## Observabilidad

Los sistemas distribuidos requieren logs, métricas y trazas. Una métrica puede indicar que la latencia aumentó durante los últimos cinco minutos. Un log puede explicar un error concreto ocurrido dentro de un servicio. Una traza puede mostrar cómo una solicitud recorrió múltiples servicios antes de producir una respuesta. Estas señales proporcionan perspectivas diferentes sobre el comportamiento del sistema. Los logs suelen contener información detallada sobre eventos individuales. Las métricas permiten observar tendencias y detectar cambios rápidamente. Las trazas permiten reconstruir el recorrido de una operación distribuida. Sin correlación entre las señales, investigar incidentes puede resultar considerablemente más difícil. Un identificador de correlación puede ayudar a relacionar eventos pertenecientes a una misma solicitud. OpenTelemetry permite instrumentar aplicaciones para producir señales de observabilidad de forma estandarizada. Los datos pueden enviarse posteriormente hacia diferentes sistemas especializados de almacenamiento y visualización. Una arquitectura observable también debe definir qué información debe capturarse y durante cuánto tiempo. Registrar absolutamente todo puede generar costos elevados y dificultar la identificación de información relevante. La observabilidad debe permitir responder preguntas concretas sobre el comportamiento del sistema durante operaciones normales y durante incidentes.

## Principio de diseño

Un buen diseño distribuido no intenta eliminar todos los fallos. Intenta hacer que los fallos sean detectables, limitados y recuperables. Cada dependencia externa debe considerarse una posible fuente de errores. Los componentes deben tener límites claros sobre los recursos que pueden consumir. Las operaciones críticas deben disponer de mecanismos de recuperación adecuados. Los sistemas deben evitar que un fallo local provoque una cascada de fallos. Las estrategias de timeout, retry y circuit breaker pueden combinarse para limitar estos efectos. La redundancia puede reducir el impacto de la pérdida de una instancia individual. La observabilidad permite detectar comportamientos anómalos antes de que se conviertan en incidentes mayores. Las pruebas de carga ayudan a descubrir límites que no son evidentes durante el desarrollo. Las pruebas de fallos pueden revelar dependencias ocultas entre componentes. Un diseño distribuido debe asumir que eventualmente algo fallará. La pregunta importante no es si un componente fallará, sino qué ocurrirá cuando falle. La arquitectura debe estar preparada para degradarse de manera controlada en lugar de colapsar completamente. Esta filosofía permite construir sistemas que continúan proporcionando valor incluso cuando partes de su infraestructura están experimentando problemas.
